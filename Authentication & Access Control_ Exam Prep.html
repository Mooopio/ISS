Authentication & Access Control

Explanation

Every secure system answers two questions in order: who are you? (authentication) and what may you do? (authorization). Part A covers the first, Part B the second. Open each block to study it.

Recap: Identification → Authentication → Authorization → Accountability. Factors: Type 1 know, Type 2 have, Type 3 are, Type 4 do / somewhere you are. MFA = two or more factors of different types. Password + PIN is still one type.
1. Identification vs authentication

Identification = claiming an identity (username, usually public). Authentication = proving it with a private factor, comparing it to the database of valid accounts. Neither alone gives access. Analogy: saying your name at the airport (identification) vs showing your passport (authentication).

2. Passwords: weaknesses and types

Weaknesses: easy to guess, written down, shared or reused, stolen (observation, replay, database theft), sent in clear text or weakly encrypted, too short.

TypeDefinitionKey point
StaticAlways the sameRisk grows the longer it is used
DynamicChanges after a time interval or number of usesLimits how long a stolen password works
One-time (OTP)Dynamic password that changes every useStrongest in concept; usually token-generated
PassphraseLong string, often a modified sentence (BlueRiverCoffeeMorning)Hard to brute-force, easy to remember
CompositionUnrelated words joined by number/symbol (Book#River9), often system-generatedWeak if the generating pattern is discovered
CognitiveAnswers to personal questions (favorite color)Weak: answers often public; do not use

Password policy = system rules on length, age, character types and reuse.

5. Storing passwords: salted, slow hashes

Hash = one-way function. The system hashes what you type and compares with the stored hash; it never decrypts. Salt = random value per password so identical passwords get different hashes. Slow hash makes each guess costly even with a stolen database. Stored = salt + hash.

Account lockout / rate limiting disables an account after set failed logons. It stops online guessing but does not protect stolen hashes. Other measures: show last logon time/place, audit logons (IDS alerts), never send passwords in clear text or email, disable inactive accounts, delete unused ones, and if the admin password is compromised change every password.

6. Biometrics

Type 3, physiological (fingerprint, face, iris, retina, palm, hand geometry) or behavioral (voice, signature dynamics, keystroke dynamics). Process: capture sample → convert to binary → store as reference template → compare live sample → accept if match passes threshold.

  • Identification (1:N): biometric instead of username; searched against all templates. Physical access (door).
  • Authentication (1:1): username first, compare with that one template. Logical access (login).
  • FRR = false rejections ÷ valid attempts (Type 1 error, threshold too strict). FAR = false acceptances ÷ unauthorized attempts (Type 2 error, threshold too lenient).
  • CER/EER = point where FRR = FAR. Same test conditions: lowest CER = most accurate.
  • Enrollment: storing the reference template; re-enroll when traits change. Throughput: scan and process time. Acceptance: privacy and comfort concerns.
  • Limits: can be spoofed (needs liveness detection); a stolen biometric cannot be changed.
7. Tokens and single sign-on
TokenHow it works
StaticFixed value, mostly identification (smart card, swipe card)
Synchronous dynamicNew password at fixed time intervals; clocks synced (authenticator app)
Asynchronous dynamicNew password on an event, e.g. button press
Challenge-responseSystem sends challenge; token computes response

SSO: authenticate once, then access resource after resource. Pros: one strong password to memorize; easier administration. Con: if the SSO account is compromised, every connected service is exposed, so protect it with MFA. Organizations trusting one identity provider let users log in once across organizations. 8. Access control: discretionary vs nondiscretionary

Authorization comes only after authentication. DAC: the owner decides, based on subject identity, via ACLs. Flexible and simple, but users can over-share and malware runs with the user’s rights. Nondiscretionary: a central rule set governs everything, not owner choice or identity: MAC, lattice, RBAC, TBAC, rule-based, ABAC.

ACL = a column (bound to an object: who can use File1?). Capability table = a row (bound to a subject: what can Ahmed use?).

9. MAC, hierarchical / compartmentalized / hybrid, and lattice

MAC uses labels: clearance (user level) and classification (data level). Access at the same or lower level and only with need to know. Each label is a security domain. Centrally enforced, owners cannot override; less flexible and scalable than DAC. Military, highest first: Top Secret, Secret, Confidential, Sensitive but Unclassified, Unclassified. Commercial: confidential, proprietary, private, sensitive, public.

  • Hierarchical: ordered levels (Public < Sensitive < Confidential < Secret < Top Secret).
  • Compartmentalized: separate areas; Project A clearance does not give Project B, even at the same level.
  • Hybrid: levels + compartments. Secret + Project A can read Secret Project A, not necessarily Secret Project B.

Lattice-based: labels in a structured order; every subject–object relationship has an upper bound and lower bound (least upper bound, greatest lower bound). Built to control information flow (confidentiality); MAC is a common example. Example range: Private (upper) to Sensitive (lower); Confidential/Proprietary and Public are no access.

10. RBAC, rule-based, ABAC

RBAC: access follows the job role (users → roles → permissions: Instructor edits final grades, TA enters coursework marks, Registrar manages enrollment). TBAC uses assigned tasks instead. Easy with staff turnover. In formal RBAC rights come only through roles; DAC groups still let users get rights directly and the owner decides.

Rule-based: predefined global rules for everyone (time, network, device). Firewall rules checked in order, ending with implicit deny. “No logins outside 08:00–18:00”, “block USB on lab PCs”. One change applies everywhere.

ABAC: rules over attributes of subject (role, department), object (type, sensitivity), action (read, edit, delete) and environment (time, location, device). Example: allow read patient_record IF role = doctor AND same ward AND within shift. Most flexible, most complex.

Trap: Role-based = who are you (your job). Rule-based = what rule applies to this request (same for all).

Smart summary

  • Auth flow: identify (claim, public) → authenticate (prove, private) → authorize → account.
  • Factors: know / have / are / do + where. MFA needs different types.
  • Passwords: static < dynamic < OTP; passphrase long and memorable; composition pattern-weak; cognitive = avoid.
    • NIST 2025: length ≥ 15 alone (8 with MFA), no composition, no forced rotation, no hints, allow 64+ and paste, block breached.
  • Attacks: sniffing, file theft, dictionary, brute force, hybrid, stuffing (reused creds), spraying (one password, many accounts), social engineering.
  • Storage: salted + slow hash, never decrypt. Lockout stops online only.
  • Biometrics: 1:N identify (doors), 1:1 authenticate (login). FRR = Type 1, FAR = Type 2, lowest CER wins.
  • Tokens: static, synchronous (time), asynchronous (event), challenge-response. SSO: convenience vs single point of failure → add MFA.
  • DAC owner/ACL · MAC labels · Lattice bounds · RBAC job · Rule-based global rules · ABAC attributes.

Common mistakes
